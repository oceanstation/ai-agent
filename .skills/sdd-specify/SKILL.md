# SDD · specify 阶段

## 何时启用
- 用户明确表达"我想按规约驱动开发做 XX"、"先出一份规约"、"开一个 feature 走 SDD 流程" 时。
- 日常对话、快速修 bug、简单问答一律**不要**用本 skill。

## 目标
把用户模糊的产品需求，转成一份可复核、可撕开来做技术方案的规约（specify.md）。

## 产出格式（严格四段）

```markdown
# <一句话概括 feature>

## 目标 Goals
- 用一句话描述该 feature 完成后带来的核心价值
- 列出 3~5 个可衡量的成功标准（先业务后技术）

## 非目标 Non-Goals
- 明确列出不做什么，避免范围蔓延
- 若用户没有明说，主动提出至少 2 条候选非目标，让用户确认

## 用户故事 User Stories
- 用 "作为 <角色>，我希望 <行为>，以便 <价值>" 的句式
- 至少覆盖一条主流程与一条边界流程

## 验收标准 Acceptance Criteria
- 用 Given/When/Then 或分点断言的方式列出
- 每条都必须可通过手工或自动化测试验证
```

## 执行步骤
1. **确认 featureId**：向用户询问一个短标识（小写字母/数字/-/_/.，例如 `user-avatar`）。若用户已提供就直接用。
2. **澄清阶段**：如需求信息不足，先用自然语言追问关键点（受众、场景、约束、优先级、成功标准）。这一步可以多轮。
3. **草拟规约**：把草拟内容以 Markdown 展示给用户看，简短点评每段的取舍。
4. **写入产物**：用户默认认可后，调用 `sdd_write_artifact` 写入：
   - `featureId`: 上一步确认的标识
   - `phase`: `'specify'`
   - `content`: 完整四段 Markdown
5. **交付**：告知用户产物已生成、路径何在，并提醒 "审阅后点批准即可进入 plan 阶段"。**不要**主动催促用户批准。

## 常见错误
- 用一句话概括代替四段结构 → 不合规
- 用工具名或参数细节回复用户 → 请用自然语言
- 不确认 featureId 就直接写入 → 违反命名约定会被工具拒绝
