# SDD · plan 阶段

## 前置条件
- 该 feature 的 `specify` 已被用户显式批准（否则 `sdd_write_artifact` 会拒绝写入）。
- 使用本 skill 前必须先 `sdd_read_artifact(featureId, phase='specify')` 拉回上一阶段结论。**不要**凭对话上下文记忆。

## 目标
把规约翻译成技术上可执行的实施蓝图，让 tasks 阶段能直接据此拆任务。

## 产出格式

```markdown
# <feature> · 技术方案

## 技术栈与关键依赖
- 语言 / 框架 / 主要依赖库（版本或范围）
- 简述选型理由（1~2 句，避免大段综述）

## 架构决策
- 分层 / 数据流 / 接口契约 / 错误策略等重要决定
- 使用小标题分组；每条决策末尾用一句话说明"为什么这么选"

## 关键文件清单
- `path/to/file.ts` — 作用一句话
- 至少覆盖新建与需要修改的文件；prefer 修改现有文件

## 测试策略
- 单元 / 集成 / 端到端 各覆盖哪些点
- 手工验证清单（若无法完全自动化）

## 风险与回滚
- 3~5 条风险；每条给出规避或回滚办法
```

## 执行步骤
1. **加载前置**：调用 `sdd_read_artifact({ featureId, phase: 'specify' })`，取回规约原文。
2. **勘察代码**：如需了解现有实现，使用 `list_dir` + `read_file` 侦察（不要盲写）。
3. **草拟方案**：面向用户简短说明关键决策，再展示完整 Markdown 供审阅。
4. **写入产物**：`sdd_write_artifact({ featureId, phase: 'plan', content })`。
5. **收尾**：说明产物路径，提醒用户审阅后批准进入 tasks。

## 常见错误
- 忽略 specify 的验收标准，方案与规约不对应
- 关键文件清单只写"新增文件"，忽略需要改动的现有文件
- 没有测试策略；plan 阶段必须给出可验证方式
